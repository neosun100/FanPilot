# FanPilot 开发计划

> 前置调研与全部实测数据：[`SMC-RESEARCH.md`](SMC-RESEARCH.md)
> 制定日期：2026-09-13 · 目标机器：MacBook Pro M5 Max (Mac17,6) / macOS 26.6.2

## 1. 需求（来自使用者）

| # | 需求 | 可行性 | 实测依据 |
|---|---|:--:|---|
| R1 | 按当前温度自动控制转速 | ✅ | `F*Tg` 可写(attr `0xd4`)、`Tp*` 23 个键随负载变化 |
| R2 | **最低转速可设，默认 2000 RPM** | ✅ | 硬件下限 `F*Mn=1350` < 2000 ✓ |
| R3 | **上限可设** | ✅ | 硬件上限 `F0Mx=5349` / `F1Mx=5777` |
| R4 | 过程**丝滑**，不突变、不抖动 | ✅ | 需算法保证，见 §3 |
| R5 | 菜单栏显示**当前温度 + 转速** | ✅ | 读取免 root，单周期 3.66ms |
| R6 | 装上就不用管 | ✅ | 守护自治 + 配置文件 |
| **R7** | ⭐ **自身几乎不占系统资源** | ✅ | 实测 2s 轮询 **0.183%** CPU，见 §1.2 |

## 1.1 ⛔ 与 TempMonitor 的边界（别混淆）

| | **TempMonitor** | **FanPilot（本项目）** |
|---|---|---|
| 控制对象 | **蓝牙外接半导体（帕尔贴）散热器** | **机内两个风扇** |
| 通道 | Bluetooth | SMC（IOKit） |
| 是否本项目管 | ❌ **完全不管** | ✅ |

**两者是不同的域，没有任何重叠，也不互相抢资源。**
NewMac 对 TempMonitor 只做了**外围压制**（见下），**从未修改它本身**——
因为它的控制逻辑与外接散热器是一体的，动它就等于动散热器。
⇒ FanPilot **不接管、不替代、不干扰 TempMonitor**。被替代的只有 `Macs Fan Control`。

## 1.2 ⭐ 资源预算：本项目的一等约束

监控/调速类常驻工具**采集频率越高、CPU 占用越高、机器越慢**。
这台机器上已有血的教材（NewMac 实测）：

| 程序 | 裸奔 | 压制后 | 手段 |
|---|---:|---:|---|
| **TempMonitor** | **~52%** | **11.7%** | 手段① `cputhrottle` 占空比压到 10% + 手段② `taskpolicy -b` |
| **Stats** | 9.07% | **4.9%** | 手段0：把 8 个模块的 1s 轮询按边际成本分别放宽 |
| **FanPilot（本项目目标）** | — | **0.183%** | **手段0 内建**（见下） |

### 遵循项目既有的三层框架，但走最上面那层

NewMac `cpu-limiter/MANIFEST.md` 的优先级排序是
**手段0（减少工作量）> 手段②（改调度）> 手段①（限份额）**，
因为手段0 减少的是**真实工作量**，无需常驻守护、无副作用。

⇒ **FanPilot 是我们自己的软件，所以能把手段0 直接内建进设计**：
轮询间隔可配（默认 **2s**）、keyinfo 缓存（省掉每周期一次 IOKit 往返）、
死区抑制无谓写入。**它因此永远不需要被 `cpu-limiter` 压制** ——
这正是自研相对于第三方 App 的核心优势（第三方不给你调间隔时，只能靠外围限流）。

### 硬预算（写进 `verify.sh`，超标即验收失败）

| 指标 | 上限 | 实测/推算 |
|---|---:|---:|
| 守护 CPU（2s 轮询） | **< 0.3%** | 0.183% |
| 守护 RSS | **< 5 MB** | 纯 C，预期 ~1-2 MB |
| 亚 2ms 定时器 | **< 5 /s** | 2s 周期 ⇒ 0.5/s |
| 唤醒次数 | **< 5 /s** | 同上 |
| SMC 写入 | **< 6 次/分钟** | 死区 50 RPM + 限幅共同抑制 |

⚠️ **判据必须是进程级指标，不是整机功耗**——整机噪声跨度 10W+ 会把这点改进完全淹没
（NewMac performance-bible §4.5 实测结论）。
⭐ 发热的真实代理是 **`Deadlines (<2 ms)` 与 `Wakeups`**，不是 CPU%（同 §4.3）。

## 2. 架构

```
┌──────────────────────────────────────────┐
│ fanpilotd  （root LaunchDaemon · 自治）   │
│   ① 读 23 个 Tp* → 取最大值               │
│   ② EMA 平滑 → 曲线映射 → 变化率限幅      │
│   ③ 死区判断 → 必要时才写 F*Tg            │
│   ④ 看门狗：异常/退出 → F*md=0 交还固件   │
│   配置: /usr/local/etc/fanpilot.json      │
│   状态: /var/run/fanpilot.status.json     │
└────────────────┬─────────────────────────┘
                 │ 只读状态文件
┌────────────────▼─────────────────────────┐
│ FanPilot.app（菜单栏 · 无权限 · 可选）    │
│   显示温度+转速（自己读 SMC，免 root）    │
│   改配置文件 → 守护热加载                 │
└──────────────────────────────────────────┘
```

**为什么不用 SMJobBless/XPC**：那需要 Developer ID 证书签名才能装 helper。
改成「守护自治 + App 只读」后：无 XPC、无特权分离、无签名门槛，
且与 NewMac 现有 `cpu-limiter` 模块**同构**，可直接复用其安装/验收/卸载规程。

## 3. 控制算法（R4「丝滑」的实现）

四层串联，每层解决一个具体的抖动来源：

```
23×Tp*  →  max()  →  EMA平滑  →  分段线性曲线  →  变化率限幅  →  死区  →  写SMC
           ↑局部热点  ↑瞬时尖峰   ↑温度→转速映射    ↑阶跃突变      ↑写入churn
```

### ① 取最大值，不取平均
23 个核簇传感器取 `max`。取平均会被冷核拉低，漏掉局部热点。

### ② EMA 平滑（杀瞬时尖峰）
```
t_smooth = α · t_raw + (1-α) · t_smooth_prev
```
时间常数 ~15s（`α ≈ interval/15`）。
**依据**：实测 `Tp00` 在 70s 内极差 10.77 °C、标准差 2.07 —— 尖峰频繁，
不平滑会让风扇跟着尖峰上下窜。

### ③ 分段线性曲线（默认值，可配置）

| 温度 | 目标转速 |
|---:|---:|
| ≤ 45 °C | **2000**（R2 下限）|
| 55 °C | 2600 |
| 65 °C | 3400 |
| 75 °C | 4300 |
| ≥ 85 °C | **上限**（默认 `F*Mx`，可配置）|

**85 °C 收到上限的依据**：`Tf06`=88.81 常量，推测是固件跳闸点（未验证），
故曲线在其之下就打满，不与固件抢。
⚠️ 两风扇 `F*Mx` 不同（5349/5777）⇒ **按各自上限归一化**，不写死同值。

### ④ 变化率限幅（非对称）
- 升速 ≤ **200 RPM/s**（热了要跟得上）
- 降速 ≤ **60 RPM/s**（凉了慢慢收，避免忽大忽小的噪音变化）

非对称是关键：散热要快、安静要稳。

### ⑤ 死区（减少 SMC 写入）
`|new_target - last_written| < 50 RPM` 就不写。
**理由**：写 SMC 是本项目唯一的危险操作，能少写就少写。
实测风扇闭环自身就有 ±16~23 RPM 抖动，50 RPM 死区不损失控制精度。

## 4. 安全设计（守护侧强制）

| # | 机制 | 为什么 |
|---|---|---|
| S1 | **键白名单**：只允许写 `F0md`/`F1md`/`F0Tg`/`F1Tg` | 任何其他 SMC 键都不碰 |
| S2 | **值域校验**：目标 RPM 必须落在**运行时读到的** `F*Mn`~`F*Mx` | 不硬编码——macOS 升级可能改 |
| S3 | ⭐ **看门狗/失效安全**：进程退出（含崩溃、SIGTERM、panic）→ `F*md=0` | **最重要**。绝不把风扇留在手动低速 |
| S4 | 启动时先**存档原值**到 `/usr/local/etc/fanpilot.original.json` | 一条命令可完全还原 |
| S5 | 温度读取失败 → **立即 `F*md=0` 交还固件**，不用陈旧值继续控制 | 降级必须留痕且走安全侧 |
| S6 | 目标转速 **只升不降的紧急路径**：温度 > 90 °C 直接打满并忽略限幅 | 保护优先于丝滑 |

> S3/S5 的通则：**任何不确定的状态都退回「固件自动控制」**，那是出厂行为，永远安全。
> 本机现在的处境（被留在手动 3400、散热封顶）正是缺少这条的后果。

## 5. 分阶段计划

### Phase 0 — 写入路径验证 ⚠️ **需 root 授权，会改动当前风扇设置**

| 步骤 | 内容 | 验收判据 |
|---|---|---|
| 0.1 | 存档当前值（`F*md`/`F*Tg`）到文件 | 文件存在且含 `md=1,Tg=3400` |
| 0.2 | 写 `F0md=0` / `F1md=0`（交还固件） | 回读 `F*md==0`；`F*Ac` 开始随负载变化 |
| 0.3 | 观察 5 分钟，确认固件正常接管 | `F*Ac` 与 `Tp*max` 正相关 |
| 0.4 | 写 `F0Tg=2500` + `F0md=1`，验证能设定 | 回读 `F0Ac` 收敛到 2500±50 |
| 0.5 | kill -9 测试进程，验证 S3 看门狗 | 进程死后 `F*md` 自动回 0 |
| 0.6 | 还原 | 恢复到 0.1 存档值或固件自动 |

**这一步是整个项目的地基** —— `md=0` 能否交还固件是 S3 的前提，必须先实测。
副产品：0.2 完成后**立刻解除当前的散热封顶**。

### Phase 1 — `fanpilotd` 守护（核心，可独立交付）

- SMC 读写层（keyinfo 缓存，实测单周期 3.66ms）
- 曲线引擎（§3 五层）
- 看门狗与失效安全（§4）
- 配置热加载 + 状态文件输出
- LaunchDaemon plist + `install.sh` + `verify.sh`（照 NewMac `cpu-limiter` 的规程）

**验收**：
- CPU 占用 < 0.3%（实测推算 2s 轮询 0.183%）
- 温度上升 10 °C，转速在 30s 内跟上且**无过冲振荡**
- `kill -9` 后 5s 内 `F*md==0`
- `verify.sh` 全绿，含**反向断言**（写非白名单键必须被拒）

**做完这一阶段「装上不用管」已经达成。**

### Phase 2 — 菜单栏 App

- `NSStatusItem` 两行显示：温度 / 转速（原软件 `menubarTwoLines=1`，沿用）
- 下拉面板：两个风扇的实际/目标转速、当前曲线点、温度来源
- 曲线编辑（拖点）+ 下限/上限滑块 → 写配置文件
- 不申请任何权限，不内嵌 helper

### Phase 3 — 收尾

- 开机自启（LaunchAgent for App / LaunchDaemon 已在 Phase 1）
- 卸载脚本（**必须先 `md=0`** 再删守护）
- 迁出 `Macs Fan Control`（含它的 root helper 与 LaunchDaemon）
- 写进 NewMac 的 profile 开关与哨兵清册

## 6. 技术选型

| 部件 | 选型 | 理由 |
|---|---|---|
| 守护 | **C**（已验证的 SMC 代码可直接复用） | 无运行时依赖、启动快、内存小 |
| App | **Swift + AppKit**（`NSStatusItem`） | 菜单栏原生；SwiftUI 在状态栏上反而绕 |
| 配置 | JSON | 人可读可手改，守护热加载 |
| 构建 | Makefile（守护）+ SwiftPM/Xcode（App） | 守护要能脱离 Xcode 独立构建 |

## 7. 风险与未决

| 项 | 状态 | 处理 |
|---|---|---|
| `md=0` 是否真能交还固件 | **未验证** | Phase 0.2/0.3 实测，是 S3 地基 |
| `Tf?6` 是否为固件跳闸点 | **未验证** | 仅作曲线上界的参考，不作判据依赖 |
| 合盖/睡眠唤醒后 SMC 状态是否重置 | 未测 | Phase 1 加唤醒后重新施加逻辑 |
| macOS 升级后键变动 | 未知 | 全部上下限**运行时读取**，不硬编码（S2） |
| 与 `Macs Fan Control` 并存会互相抢写 | **确定会** | Phase 0 前必须先停掉它，否则两边打架 |

⚠️ **本项目不解决 2026-09-13 的两次 SoC 看门狗重启**（`iBoot panic`/`wdog`，固件层）。
风扇控制与那次故障无因果关系，勿混淆。
